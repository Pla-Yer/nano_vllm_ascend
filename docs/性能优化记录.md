### analysis

从上面的记录可以看出，当前decoder耗时大约53ms，layers中，RMSNorm不随token增加，说明不是算力瓶颈，而是多小算子开销；相似的，rope_full也是不随token增加而增加，在当前版本中，rope分为两部分：第一部分是 RotaryEmbedding.forward 里每次根据 position_ids 计算 freqs -> cos/sin；第二部分是 apply_rotary_pos_emb_tnd 里做 cos.to()、sin.to()、unsqueeze、rotate_half、cat、mul/add。已经做过一次优化，但耗时仍然偏高，说明后面的apply也是极大的开销；mlp，当前实现为down_proj(silu(gate_proj(x)) * up_proj(x))，是两次GEMM+silu+mul。
绝大部分计算都没有随着token增加而增加，说明计算在当前不是瓶颈，应该是调度等开销占比较大，当前阶段将把手写的计算过程变为npukernal以提高效率

### analysis

通过将手写分解算子：转 fp32、平方、mean、rsqrt、乘 weight、再 cast 回原 dtype。全过程直接转变为npu_rms_norm单算子，结果也很显然，
| 项                            |        P0 |        P1 |             变化 |
| ---------------------------- | --------: | --------: | -------------: |
| `rms_norm_hidden [1,1024]`   | 0.1683 ms | 0.0546 ms | **约 3.08× 加速** |
| `rms_norm_head [1,16,128]`   | 0.1654 ms | 0.0548 ms | **约 3.02× 加速** |
| `rms_norm_hidden [512,1024]` | 0.1641 ms | 0.0588 ms | **约 2.79× 加速** |
| `rms_norm_head [512,16,128]` | 0.1642 ms | 0.0586 ms | **约 2.80× 加速** |

端到端提升：
| 指标            |       P0 |       P1 |         变化 |
| ------------- | -------: | -------: | ---------: |
| prefill_s     | 0.0566 s | 0.0414 s | **-26.9%** |
| decode_s      | 6.8783 s | 5.0547 s | **-26.5%** |
| total_s       | 6.9349 s | 5.0961 s | **-26.5%** |
| prefill_tok/s |   547.65 |   748.88 | **+36.7%** |
| decode_tok/s  |    18.46 |    25.14 | **+36.2%** |
| total_tok/s   |    22.93 |    31.22 | **+36.1%** |
这也可以对上，单次layers的forward会进行4次norm，包括：输入input_layernorm、计算注意力时的q_norm,k_norm、以及输出前的post_attention_layernorm，qwen0.6b模型一共28层，便是28*4=112次/token，一次便可以减少约12ms。当前decode约为39.49 ms/token

## P2 RoPE
优化包括：
1. cos/sin 从“每次 forward 现算”变成初始化时预计算缓存，之前是只缓存了inv_freq，然后每次forward再计算cos与死你，现在直接缓存cos与sin；
2. 每层 apply 从多个 PyTorch 小算子变成 torch_npu.npu_rotary_mul。
